# 7.0 clear-bonus investigation plan

Live-capture protocol for item 4 of [[h-7.0-potential-rework]]: Arcaea 7.0 added a play-rating
bonus for "obtaining a Clear," DEV-STATED but with no magnitude, no `clear_type` boundary, and no
answer on whether it breaks friend-path best-50 the same way [[d-r10-impossible-friend-path]]
broke r10. Chosen over item 2 (the `/60` divisor) as the higher-risk unknown to close first — a
single unverified constant is a smaller blast radius than "the entire play-rating formula may no
longer be a pure function of `score`."

## Why it is open

Pre-7.0, [[potential|Potential]]'s play-rating formula was a pure function of `score` + chart CC
— the exact reason b30 (never r10) was friend-path-safe. If a cleared vs. failed play at the
*same score* now earns different play rating, that purity claim is false for the entire formula,
best-50 included. Nothing here is confirmed enough to guess into shipped code.

## Resources confirmed available (2026-08-28)

- A tier-3 subscribed own-credentials test account, ready to use.
- Capture via a manual HTTP toolkit hitting `webapi.lowiro.com` directly — web API only, not the
  game client.
- A second account/bot key, able to friend the test account, for the friend-path leg.

## Protocol

Five phases, each gating the next. Nothing in `b30.py`/`b30_stat.py`/`utils/scoring.py` moves
until Phase 5.

**Phase 0 — endpoint recon.** Cheap, do first. `GET /webapi/user/me` on the test account confirms
the session/tier still behaves post-7.0. `GET /webapi/score/rating/me` is the load-bearing check:
pre-7.0 it returned `best_rated_scores`/`recent_rated_scores` (30+10) with `rating` and
`clear_type` on the *same* per-entry record ([[handoff-10-score-history-backfill-research]]).
Confirm whether that shape survives (`best_rated_scores` now 50, `recent_rated_scores` gone?
renamed keys? 404, needing `score/rating_progression/me` or a neighboring path instead?) and
whether `rating` + `clear_type` are still both present per entry — Phase 1 depends on it.

**Phase 1 — passive residual analysis.** One request, no new plays needed. For every entry
returned, compute `expected = cc + base_formula(score)` from [[potential|Potential]]'s pre-7.0
encoding (the base term the 7.0 bonus adds on top of, per the tweet) against the chart's catalog
CC; `residual = actual_rating − expected`. Group residuals by `clear_type`. Pre-7.0 all residuals
were ~0 (the formula was pure); post-7.0, if the bonus is real and clear-gated, `TRACK_LOST`
should stay ~0 while other `clear_type` values show a consistent positive residual. Gives a
first-pass magnitude, a first-pass score-range read (plot residual vs. score), and a first-pass
`clear_type` boundary — all free, from plays the account already has. Limited by how much
`clear_type` variety already sits in the account's own best-50 (likely thin on `TRACK_LOST` for a
well-maintained account), which Phase 2 exists to fill.

**Phase 2 — controlled matched-pair captures.** `GET rating/me` → play → `GET rating/me` → diff
the touched entry, on 1-2 charts safe to perturb (kept outside the top 10 for now, see Phase 3).
Same chart, matched score, `TRACK_LOST` vs. `CLEAR` isolates the bonus controlling for score.
Repeat with `HARD_CLEAR` and `EASY_CLEAR` at matched score to test whether every non-`TRACK_LOST`
type gets an identical bonus or a graded one. Repeat once with a hard-gauge `TRACK_LOST`
(`modifier == HARD`) specifically — the old recent-30 hard-gauge exclusion is gone with r10, so
confirm this still nets zero bonus rather than being picked up as some new special case. Repeat
near each score-band boundary (9,499,999/9,500,001; 9,799,999/9,800,001; 9,999,999/10,000,000) at
matched `clear_type` to check whether the bonus is flat or scales with the base formula's
segments. Log per capture: UTC timestamp, chart, submitted score, ground-truth clear result (read
off the game, not inferred), raw before/after JSON, computed delta.

**Phase 3 — isolate from item 2.** The best-50 reshape and the clear bonus are two independent
7.0 changes landing at once. Run Phase 2's pairs on charts outside the top 10 first so the
doubling can't confound the bonus reading; once the bonus is nailed down, repeat one pair on a
top-10-ranked chart to confirm it doubles there too, or doesn't (if the top-10 slice recomputes
independently from a different base).

**Phase 4 — friend-path correlation.** Before any Phase 2 play, pull `GET /webapi/friend/me` from
the second account and record the test account's `recent_score` entry verbatim — confirm it is
still exactly the 5-field shape `coda/arcaea/dto/score.py::from_friend_wire` assumes (`song_id`,
`difficulty`, `score`, `time_played`, the friend's own `arc_user_id`); 7.0 is exactly the kind of
change that could have quietly grown this. After each Phase 2 play, pull `friend/me` again and
diff. Expected, by analogy with [[d-r10-impossible-friend-path]]: nothing distinguishes
`clear_type` — `time_played` is a submission timestamp, not song-position, so it carries no
early-submit signal either. Confirm empirically rather than assume. Also diff the friend's
aggregate `rating` (PTT) delta against the own-credentials aggregate delta from `rating/me` for
the same play: if they match, the *aggregate* PTT is trustworthy cross-path even though per-chart
best-50 reconstruction is not — the precise distinction the eventual write-up needs to draw.

**Phase 5 — write-up / decision gate.** Once magnitude, `clear_type` boundary, score-range
behavior, and the friend-path answer are captured: update [[h-7.0-potential-rework]] items 2 and
4, update [[potential|Potential]] §Encoding with the real formula, and only then touch `b30.py`/
`b30_stat.py`/`utils/scoring.py`. If the friend path shows no signal (expected): file a new
decision analogous to [[d-r10-impossible-friend-path]] — best-50 is exact on own-credentials tier
only, and the friend-path figure must say so rather than silently approximate.

## Answer

**Phase 0 + Phase 1 executed 2026-08-31** (owner capture, own-credentials, tier-3 test account —
not the account originally scoped for this protocol, but same method).

Phase 0: `GET /webapi/score/rating/me` still responds post-7.0, shape is `{ best_rated_scores: [...] }`
— 50 entries as the 7.0 announcement said, `recent_rated_scores` is gone (expected, r10 removed).
Each entry carries `rating`, `score`, `clear_type`, `modifier`, `difficulty`, `song_id` on the same
record — Phase 1 unblocked.

Phase 1: for every one of the 50 entries, computed `expected = cc + base_formula(score)` against
the chart's live catalog CC (`song_difficulties.rating / 10`, matched by `song_id` + difficulty
ordinal) and diffed against the wire `rating`. **Every single entry residual`= actual − expected`
came out to exactly `+0.200000`** (6 decimal places, no floating noise) — confirmed:

- **Magnitude: flat `+0.2`**, not scaled by score, CC, or score-formula segment. Entries span
  CC 10.7–12.0, score 9,706,993–10,001,493 (crossing the 9.8M boundary, one entry >10M from a MAX
  bonus) — residual never moved.
- **Applies uniformly across every `clear_type` present**: `CLEAR`(1, ×27), `FULL_RECALL`(2, ×9),
  `PURE_MEMORY`(3, ×1), `HARD_CLEAR`(5, ×13) all showed the same `+0.2`.
- **Applies under both gauge modifiers present**: `NORMAL`(0, ×33) and `HARD`(2, ×17) both showed
  the same `+0.2` — the bonus is not gauge-conditional the way the old hard-gauge recent-30
  exclusion was ([[d-hard-gauge-early-submit]]).

**Not answered by this capture** — a 50-best pool structurally cannot contain the missing cases:
- `TRACK_LOST` (clear_type=0) — 0 entries. Cannot distinguish "no bonus on a loss" from "bonus
  keys off something looser than clear status." The `clear_type != 0` working assumption in
  [[potential|Potential]] §Encoding is *not yet proven*, only *not contradicted*.
- `EASY_CLEAR` (clear_type=4) — 0 entries. Given every other non-lost type is uniformly `+0.2`,
  a different value here would be surprising, but unverified is unverified.
- Friend-path behavior (Phase 4) — untouched, needs the second account.

**Phase 4 executed 2026-08-31** (owner capture, `new_friend_res.json`, 20 friends). Every
`recent_score` entry is exactly `{time_played, score, difficulty, song_id, title}` — no
`clear_type`, no `modifier`, on any of the 20. Matches `from_friend_wire`'s tier-1 parsing
(`arcaea/dto/score.py:64`) and confirms rather than assumes: the friend path structurally cannot
see clear status post-7.0, same shape as pre-7.0. If the clear bonus is `clear_type`-gated,
best-50 inherits r10's old friend-path gap exactly as [[d-r10-impossible-friend-path]] predicted
— confirmed, not just analogized.

**Phase 2 attempted 2026-08-31, inconclusive** — owner played `balor` PRS (`TRACK_LOST`,
score 9,948,633) and `cataclysmcry` PST (`EASY_CLEAR`, modifier `EASY`, score 9,930,221) as a
matched pair. Both charts turned out to have **unrated/TBA CC** in the catalog
(`song_difficulties.rating = 0` for both slots — `cataclysmcry` even shows the split within the
same song: PRS=8.8 and BYD=11.8 are real, PST and FTR are still `0`). Per
[[d-unknown-cc-no-play-rating]] neither play can produce a computable play rating at all, so
neither can enter `best_rated_scores` regardless of clear status — wrong chart pair for the
residual method. No before/after `rating/me` diff was captured to confirm this directly.

**Working assumption recorded 2026-08-31 (owner, NOT live-verified — cannot test right now):**
`TRACK_LOST → +0.0` (no bonus), `EASY_CLEAR → +0.2` (same flat bonus as every other clear type
Phase 1 measured). This is the owner's best-guess call to unblock forward work, not a capture
result — treat as provisional. It is consistent with everything Phase 1 actually measured (every
non-`TRACK_LOST` type present was uniformly `+0.2`, so `EASY_CLEAR` following suit is the
unsurprising case) and with the plain reading of "obtaining a Clear" (a `TRACK_LOST` play, by
definition, did not obtain one). **Still needs a real Phase 2 capture** — matched-score
`TRACK_LOST` vs. `CLEAR` on a chart with known CC, ideally already in the best-50 so a worse play
can't accidentally enter it — before code treats this as settled.

**Status of `b30.py`/`b30_stat.py`/`utils/scoring.py`**: still untouched per Phase 5's gate. The
flat `+0.2` magnitude is confirmed and safe to encode; the `clear_type` boundary is an assumption,
not a capture — a port that hardcodes `clear_type != 0` today would be encoding a guess, not a
verified fact. Owner's call on whether that's an acceptable risk to ship on.
